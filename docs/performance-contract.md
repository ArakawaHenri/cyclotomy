# 性能假设与验收预算

状态：GC 与捕获优化的拟定验收契约。以下数字是目标，不是 0.2.4 已达到的测量结果；在参考环境登记和基线生成之前，不能宣布通过。

## 1. 最终校验的等价性边界

基准语义是现有 `workspaceSnapshotsEqual`：根路径、Git evaluator、scope、所有文件内容标识、排除项和目录身份均一致。最终验证还重新发现外部 Git 策略来源。

H1：发布阶段认证变更文件后，以目录稳定性、每文件 stat 收据和已有哈希代替最终全量内容扫描。

**在当前支持的普通本地文件系统契约下，不接受 H1。** 已识别的变更全部认证，不等于能够识别全部变更。

反例：第一次扫描和发布之后，另一写入者原地改写一个文件，长度不变、inode 不变，在时间戳粒度内得到相同的可观察 stat 收据。目录项未改变。stat 方案会复用原哈希，而第二次内容扫描会发现字节不同。增加 ctime 检查仍不使时间戳变成跨文件系统保证唯一的内容版本号。Git 的 racy stat cache 问题提供了相关先例。[Git 文档](https://git-scm.com/docs/racy-git)

另外，只检查工作区目录和文件无法替代全局 Git 配置、外部 excludes 等策略的重新发现。即使补足策略检查，前述内容反例仍需要解决。

捕获保留两次完整内容观察。未来只有在引入可证明的文件系统快照或可靠变更版本来源后，才能重新讨论替代校验。两次观察一致也不等于原子文件系统快照，不宣称它能对抗任意外部并发写入调度。

## 2. 可证伪的优化候选

| 假设                               | 正确性条件                                                                   | 效果条件                                                                                     | 不通过时                                  |
| ---------------------------------- | ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------- |
| H2：同操作内复用树的结构规范性结果 | 绑定结构对象身份；变化时重新验证或失败；不能把内存缓存当作 GC 的持久存活副本 | 稳定树重复读取的规范重建最多一次；该基准中位耗时至少下降 20%                                 | 保留原实现                                |
| H3：首次扫描与新增内容发布协作     | 不取消最终扫描；输入变化、scope 变化和取消结果与基线一致；树 OID 相同        | 全新唯一内容场景的工作区读取字节至少下降 25%，中位耗时至少下降 10%，总 I/O 字节不增加超过 5% | 拒绝仅把工作区读取搬成更多暂存 I/O 的方案 |
| H4：把全局 mark 集转为磁盘工作集   | 删除范围与基线一致；表示依赖、重入引用和中断规则成立                         | 固定单树规模、历史根扩大十倍时满足 GC 预算                                                   | 不宣称已解除历史总量限制                  |

H2 只复用结构规范性和语义 manifest。内容健康、物理提供者和删除依据仍各自验证。H3 使用总量受限的缓冲或暂存，不按并发 lane 各自领取完整内存预算。

## 3. 参考环境与数据集

首期数值门槛使用固定 R1：Linux x86_64，4 个固定 CPU 执行单元、16 GiB RAM、本地 NVMe、ext4，Node 24.15.0、Pi/TUI 0.85.1、Git 2.55.0。登记实际 CPU 型号、SSD、内核、频率策略与机器标识，之后不跨机器混比。若使用现有硬件替代这一模板，应在生成基线前固定新的环境清单和预算，不在优化完成后修改标准。

macOS、Windows 始终运行功能、资源上界、原生依赖和崩溃恢复门槛；固定平台参考机建立之前，共享 CI 的壁钟时间作为趋势，不用其噪声声称性能达标。

固定内容种子与夹具校验和。捕获先预热 3 次、测量 20 次，报告中位数与 p95；大型 GC 使用 5 份相同起点的独立夹具副本，报告最慢值。夹具准备不计时，GC 不能在第一次删除完后复用已经变小的仓库充当重复测量。

| 数据集 | 固定内容                                                                                                                |
| ------ | ----------------------------------------------------------------------------------------------------------------------- |
| P1     | 10,000 个受观察条目，总内容 100 MiB；分别测试无变更、1% 变更和全新内容                                                  |
| P2     | 接近 100,000 个受观察条目，总内容接近 2 GiB，单文件不超过 50 MiB                                                        |
| G1/G10 | 每棵树 1,000 个文件，初始各 1 KiB；每新增根只改一个文件的 16 字节；分别 1,000/10,000 个根，额外构造相同比例的无引用数据 |
| Q      | 1,000 个会话、100,000 个 slot，用于只读 CLI 查询                                                                        |

条目数包含根和目录。所有比值使用相同编码、压实配置与缓存条件；暖缓存是首期门槛，冷缓存另外报告。

## 4. 数字门槛

| 范围                               | 拟定验收值                                                                                               |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Q 的 doctor 快速检查               | p95 ≤ 1 秒；忙碌或未检查必须明确返回，不能为满足时限省略诊断却宣称健康                                   |
| Q 的 history 首 100 个会话         | p95 ≤ 1 秒；准确计数与估算字段分开                                                                       |
| G10 对 G1 的 GC 峰值 RSS 增量      | ≤ 128 MiB，单树规模保持不变                                                                              |
| G10 对 G1 的完整 GC 耗时比         | ≤ 15，防止明显超线性退化；不宣称 GC 为常数成本                                                           |
| 自动维护的前台占用                 | 拟定预算 1 秒；R1 小型合格数据集 p95 ≤ 1.5 秒，预算不足返回 maintenance-needed，不允许不完整 mark 后删除 |
| Cyclotomy 自己持有的额外文件描述符 | 峰值 ≤ 64，操作排空后回到基线                                                                            |
| H3 额外内容缓冲总量                | ≤ 64 MiB，包含队列和所有在途任务                                                                         |
| 其他 P1/P2 场景的性能回归          | p95 耗时及峰值 RSS 不超过同环境基线的 110%                                                               |
| 取消                               | 停止领取新工作；在途数量不超过配置上限，排空后没有新增元数据提交或资源泄漏                               |

自动维护的完整标记若不适合预算，就转为维护窗口；不能反复从头阻塞每次 turn_end。大仓库通过 CLI 明确运行完整维护，其进度、取消和结果需可观察。

性能变更必须附测量工具、环境清单、基线与原始结果。修改预算是单独的设计变更，不能通过事后调阈值使同一失败通过。

“理解路径更短”由结构验收表达：关键持久状态有唯一写入所有者，操作完成只有一个协调出口，Presenter 不再自行判断授权。它不代替性能指标，也不以删行数作为完成条件。

## 5. 运行测量

`npm run test:performance:gc` 使用独立 Node 进程运行 `scripts/gc-performance.ts`，显式启用 GC 并输出 JSON 原始指标。它不属于 `npm test` 的功能测试集合。默认 G1/G10 为 32/320 个根，每棵树 64 个文件，适合本地观察趋势。

在登记的 R1 参考机使用完整 GC 数据集：

```sh
CYCLOTOMY_GC_BENCH_ROOTS=1000 CYCLOTOMY_GC_BENCH_FILES=1000 npm run test:performance:gc
```

一次运行报告耗时、峰值 RSS、文件描述符和回收结果；完整验收仍须按上文准备独立夹具副本并重复采样。脚本验证保留内容、回收结果和预算耗尽时的停止边界；实际指标必须与拟定预算比较，不能以测量值存在或比值为正代替达标证据。
